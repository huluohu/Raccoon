# 06 · 配置中心详细设计

> 对应方案 §6。界面是配置主要操作入口；环境变量只保留启动必需项与运维覆盖项，被锁定的配置在界面只读并标注来源。

---

## 1. 五要素注册表

每项设置 = 一行注册定义（代码内 `internal/config/registry.go`）+ DB 当前值（settings 表）：

| 要素 | 注册字段 | 说明 |
| --- | --- | --- |
| 说明 | `desc` | 人话：影响什么、默认行为 |
| 默认值 | `def` | 开箱即用，常用路径零配置 |
| 校验规则 | `validate` | 路径存在性/URL 格式/数值范围/枚举 |
| 敏感级别 | `sensitive` | 凭据类打码、单独保存、不进普通导出 |
| 生效时机 | `effective` | immediate / next_task / restart |

## 2. 三类生效时机的实现机制

| 时机 | 实现 | 典型设置 |
| --- | --- | --- |
| immediate | 内存配置原子热替换 + 广播 `config.changed(SSE)` + 前端即时生效 | 界面偏好、密度、深色模式、通知规则 |
| next_task | 写入 settings 表 + 版本号 +1；任务创建时读取当前 version 快照进 `tasks.config_version` | 下载质量、保存命名、代理、平台账号 |
| restart | 写入并标记 pending_restart；`/system/info` 返回 `restart_required:true`，界面顶部提示条 | 监听端口、数据目录、DB 路径 |

- 运行中任务使用创建时固化的 config_version——「保存后新任务生效，旧任务不漂移」。
- 需重启项保存时明确列出影响范围（如「改端口将断开当前所有 Web 连接」）。

## 3. 保存流程（方案 §6.3 五步）

```
PUT /config
 1. 校验：逐项 validate → 失败定位到具体字段（VALIDATION + details）
 2. 检查：连接类（qb/115/telegram）先 test-connection；路径类查存在性与可写性
 3. 持久化：ElemSet 逐项写 value_json + version+1 + setting_history 留痕（单事务）
 4. 应用：按 effective 执行（热替换/版本递增/pending_restart 标记）
 5. 反馈：返回 {saved:[...], effective_summary:{immediate:[], next_task:[], restart:[]}}
    ——「已保存，将于下一个任务生效」必须是接口明确返回的语义，不是前端猜的
```

- 失败即整体回滚（事务），保留上一份有效配置——不会出现「界面说成功，服务没用上」。

## 4. 环境变量锁定

- 启动时：`RACCOON_<KEY_PATH>` 形式的环境变量覆盖写入内存配置并标记 `locked_by_env`（如 `RACCOON_SERVER_PORT=8530` → `server.port`）。
- 界面：锁定项只读展示 + 标注来源变量名；PUT 锁定键返回 409 `LOCKED_BY_ENV`。
- 运维改这类配置只能改环境变量并重启容器——不走界面回改，避免两份配置打架（方案 §6.4）。

## 5. 历史、导出与凭据保护

| 能力 | 规则 |
| --- | --- |
| 配置历史 | 每次保存一条 setting_history（key/version/时间/操作人），保留最近 50 条/键 |
| 回滚 | POST /config/rollback {key, version} → 写入新版本（前进一步，非物理回退），可再次前进 |
| 导出 | GET /config/export：默认**不含**敏感项明文；勾选包含时导出前预览明示风险，文件加密提示 |
| 导入 | 先校验 + 列 diff → 用户确认后应用；凭据类不接受普通导入（走 credentials 端点单独上传） |
| 凭据变更 | Cookie/Token 的更新与撤销只经 credentials 模块，普通配置回滚不能悄悄恢复已撤销密钥 |
