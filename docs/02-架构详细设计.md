# 02 · 架构详细设计

> 对应《整体方案 v2.4》第 4、5、7、11 章。原则：一个容器、一套登录、一份配置、一个任务队列；平台差异收敛在适配层。

**架构决策记录（ADR 摘要，完整版见 §5）**：

| # | 决策 | 选择 | 备选（否决理由） |
| --- | --- | --- | --- |
| ADR-1 | HTTP 框架 | 标准库 `net/http` + 自建轻量 Router（路由树 + 中间件链，约 200 行） | Gin/Echo：骨架阶段零外部依赖可离线构建；路由量（约 60 个端点）未到必须引入框架的规模；后续按需替换不影响分层 |
| ADR-2 | 进程模型 | 单进程 + 进程内 Worker 池；队列表持久化在 SQLite | 独立 worker 进程：首发引入 IPC/心跳/恢复复杂度，收益仅是「网页不卡」——而下载本就是异步 goroutine，网页线程本就无阻塞风险；队列表已保证进程崩溃后可恢复（§5.2 恢复流程） |
| ADR-3 | 数据库驱动 | modernc.org/sqlite（纯 Go，无 cgo） | mattn/go-sqlite3：需 cgo，交叉编译与静态分发受损（方案 §4.2 已确认） |
| ADR-4 | 进度推送 | SSE（`/api/v1/events`）+ 前端轮询兜底 | WebSocket：双向能力用不上；SSE 断线自动重连语义更简单 |
| ADR-5 | 前端托管 | `embed.FS` 内嵌构建产物，单端口部署 | 独立静态服务：多一个容器/端口，违背「一个 Web 端口」（§7） |

## 2. 模块划分与代码目录映射（方案 §5.1 七模块）

| 方案模块 | 职责 | 代码位置（internal/） | 对外暴露 |
| --- | --- | --- | --- |
| 接口与登录 | 入口鉴权、账号体系 | `server`（中间件）+ `auth` | REST、Bot、CLI |
| 任务调度 | 队列、并发、状态机、恢复 | `task`（scheduler/state/store） | Service 接口 |
| 平台解析与下载适配 | 固定接口 Adapter | `engine`（adapters/ytdlp、gallerydl、qbittorrent、n115） | Engine 接口 |
| 订阅与录制 | 订阅检查、直播编排 | `subscription`、`live` | Service 接口 |
| 文件和存储 | 落盘、命名规则、后处理、调度 | `storage`、`media`（ffmpeg 后处理） | Service 接口 |
| 配置与连接管理 | 配置中心、凭据、健康检查 | `config`、`credential` | Service 接口 |
| 通知、日志与诊断 | 通知渠道、结构化日志、诊断包 | `notify`、`diag`、`logx` | Service 接口 |

依赖方向（单向无环）：

```
cmd/raccoon
   └─► server ──► auth
        └─► service 层（编排：task/subscription/live/media/storage/config/credential）
                └─► engine（adapters 只依赖 engine 定义的接口，不反向依赖 service）
                └─► store（SQLite 访问，唯一数据出口）
   notify ◄── task（任务事件 → 通知；notify 不依赖 task）
   logx / diag 被所有层使用，不依赖任何业务层
```

模块边界审查（software-project 第三步点五）：

| 维度 | 结论 |
| --- | --- |
| 依赖方向 | 无环：engine/store/logx/notify 为底层，service 编排，server 为入口层 |
| 接口契约 | 跨模块一律走接口（Engine、Store、Notifier），禁止跨模块访问内部结构体字段 |
| 数据持有 | 表 → 归属模块唯一：tasks/task_events/subtasks → task；credentials → credential；users/api_tokens → auth；files → storage；其余按前缀归属 |
| 变更半径 | 单平台改动只触达对应 adapter 文件 + 注册表一行 |
| 术语一致性 | Task/TaskEvent/Subscription/LiveSource/Credential/Setting 全仓同名同义 |

## 4. 请求生命周期（以「添加任务」为例）

1. `POST /api/v1/tasks` → router → auth 中间件（Session/Token）→ CSRF 校验
2. → handler 参数校验（URL 列表、非空、长度上限 500）
3. → service.TaskService.Create：查重（dedupe key）→ 解析平台选择 adapter → 写 tasks 表（status=waiting）+ task_events
4. → scheduler 唤醒：额度允许 → waiting→parsing → engine 执行（受管子进程，带超时与取消 context）
5. → 进度通过 task_events + SSE 广播；终态写 files 记录 + 通知
6. → 前端列表/详情由 SSE 事件驱动刷新，禁止前端自行推算状态

## 5. 安全设计（映射方案 §11）

| 方案要求 | 实现机制 | 落点 |
| --- | --- | --- |
| 初始化管理账号，不用默认密码 | 首次启动检测 users 空 → 强制走 /setup 初始化流程，未初始化前管理 API 全部 428 | `auth` + `server` 中间件 |
| 密码安全哈希 | Argon2id（golang.org/x/crypto，锁版本） | `auth` |
| 凭据加密保存 | AES-256-GCM，密钥来源于首次初始化生成的主密钥（存 data/keys/master.key，权限 0600）；Cookie 文件同样加密 | `credential` |
| API 凭据可撤销/范围/有效期 | api_tokens 表：scope 位掩码 + expires_at + revoked_at；每次请求校验 | `auth` |
| 下载地址防内网探测/重定向绕过/危险协议 | URL 协议白名单（http/https/magnet）；解析域名 → 拒绝私网/环回/链路本地（用户显式配置代理除外）；重定向逐跳复查（上限 5 跳） | `engine/ssrf.go` |
| 防路径穿越 | 所有用户输入路径经 `storage.SafeJoin(root, rel)`：清洗后必须 root 前缀 + 不允许 `..`/绝对路径/符号链接逃逸 | `storage` |
| 命令注入 | 外部命令一律 `exec.CommandContext(name, args...)` 参数化，禁用 shell 拼接；参数来自白名单枚举 | `engine` 全局铁律 |
| 日志与诊断脱敏 | logx 脱敏器（Cookie/Token/密码字段名 → `***`）；诊断包导出前预览 + 强制脱敏 | `logx` / `diag` |
| 远程访问 | 默认只监听容器内端口；文档引导反代/VPN，不默认暴露公网。容器用 `network_mode: bridge` 接入默认网桥，保证宿主机与反代容器能稳定访问映射端口（反代上游写宿主机端口而非容器端口，见部署文档 §6） | 部署文档 |
| 授权边界 | 不含原版授权校验代码；不破解第三方付费服务 | 纪律约束 |

## 6. 可观测性

| 项 | 方案 |
| --- | --- |
| 结构化日志 | JSON 行，字段：ts/level/msg/module/task_id/request_id；落 data/logs/raccoon.log（轮转 10MB×5） |
| 关键指标 | 队列深度、各状态任务数、worker 占用、引擎子进程数、磁盘余量（/metrics JSON 端点，供排障不引 Prometheus） |
| 健康检查 | `GET /api/v1/health`：进程活着 + DB 可写 + 数据目录可写；供容器 healthcheck |
| 诊断包 | `GET /api/v1/diag/export`：脱敏后的最近日志 + 配置快照 + 任务状态统计，导出前预览 |
| 告警 | 应用内通知中心为主；外部渠道（Telegram）按设置推送；不内置邮件/SMS |

## 7. 数据与部署拓扑

单容器、单端口（默认 8530，对齐开源版习惯）、单数据目录 `/data`：

```
/data/
├── raccoon.db            # SQLite（WAL 模式）
├── config/               # 配置导出入、引擎临时配置
├── credentials/          # 加密后的凭据（cookies/账号/token）
├── logs/                 # raccoon.log + engine 日志
└── downloads/            # 默认下载目录（可在设置改容器内路径）
```

第二个挂载（可选）：`/media` 指到用户已有 NAS 媒体库，下载目录可切换其中子路径（§7 挂载策略演进）。不挂 docker.sock；「重启应用服务」为进程内优雅重启（重新加载配置 + 恢复队列），非宿主容器重启。

## 8. 失败模式与边界

| 场景 | 行为 |
| --- | --- |
| worker 崩溃（panic） | recover + 任务回 waiting 带「引擎异常退出」原因，尝试次数 +1 |
| 进程整体退出 | 重启后 scheduler 扫描：parsing/downloading/post → 按引擎能力恢复或回 waiting；失败原因如实标注 |
| SQLite 锁竞争 | WAL + busy_timeout=5000；写操作串行化经单写goroutine 队列 |
| 磁盘写满 | 后处理/下载失败 + 全局预警条 + 暂停新下载任务入队执行 |
| 引擎二进制缺失 | 启动自检：缺 yt-dlp/FFmpeg → 健康检查失败 + 日志明确缺哪个 |
